# Developer Spec-Kit — Vanilla Frontend Implementation

```yaml
role: Senior Frontend Engineer
tech_stack:
  - Semantic HTML5
  - Standard CSS3
  - Modern JavaScript (ES6+)
architecture: Vanilla, modular when useful
constraints:
  - No UI framework unless explicitly requested
  - No build tools unless explicitly requested
  - No unnecessary production dependencies
focus:
  - Correctness
  - Maintainability
  - Responsive behavior
  - Accessibility
  - Performance
  - Safe DOM updates
```

## 0. 개발 원칙 및 적용 범위

이 문서는 AI 코딩 에이전트가 사이트를 구현·수정할 때 따를 기본 규칙입니다.

1. **기존 프로젝트 우선:** 이미 존재하는 파일 구조, 네이밍, 구현 패턴을 먼저 파악합니다. 요청 없이 전체 구조를 재작성하거나 프레임워크를 도입하지 않습니다.
2. **요구사항 우선:** 사용자가 제공한 HTML, CSS, JS, 이미지, 시안, 명세를 기준으로 구현합니다. 자료에 없는 기능이나 콘텐츠를 임의로 추가하지 않습니다.
3. **최소 변경:** 요청한 범위에 집중하고 관련 없는 코드와 디자인을 불필요하게 수정하지 않습니다.
4. **단순한 구현 우선:** Vanilla 프로젝트에 복잡한 상태 관리 시스템이나 추상화 계층을 무조건 도입하지 않습니다.
5. **실행 가능한 결과:** 코드 작성 후 문법, 경로, 반응형 동작, 콘솔 오류 가능성을 점검합니다. 실제로 실행하지 않았다면 테스트 완료라고 주장하지 않습니다.

## 1. 기술 및 프로젝트 구조

### 1.1 기본 기술 규칙

- HTML5, CSS3, JavaScript ES6+를 사용합니다.
- 사용자가 허용하지 않은 React, Vue, Svelte 등의 프레임워크를 도입하지 않습니다.
- 빌드 도구와 패키지 매니저는 프로젝트에 이미 있거나 사용자가 요청한 경우에만 사용합니다.
- 외부 라이브러리는 기본적으로 사용하지 않습니다. 꼭 필요한 경우 도입 이유, 버전, CDN 또는 설치 방법을 명시하고 기존 제약을 확인합니다.
- ES Modules(`import`/`export`)를 사용하는 경우 로컬 개발 서버 또는 HTTP 환경에서 실행합니다. `file://` 직접 열기에서는 브라우저 보안 정책으로 모듈 로딩이 제한될 수 있습니다.

### 1.2 권장 디렉토리 구조

프로젝트 규모에 맞게 선택합니다. 작은 랜딩 페이지나 단일 페이지는 단일 HTML 파일 또는 소수의 파일로 유지해도 됩니다.

```text
project-root/
├── index.html
├── css/
│   ├── reset.css
│   ├── variables.css
│   ├── base.css
│   ├── layout.css
│   └── components.css
├── js/
│   ├── app.js
│   ├── components/
│   └── utils/
└── images/
```

- 기존 프로젝트의 디렉토리 구조가 있다면 이를 우선합니다.
- 파일을 분리할 때는 책임이 명확하고 재사용 가치가 있는 경우에만 분리합니다.
- CSS는 프로젝트 규모에 따라 하나의 파일로 관리하거나 역할별로 분리합니다.
- 이미지·폰트 등 정적 자산의 경로는 실제 프로젝트 경로를 확인해 사용합니다.

## 2. HTML 작성 규칙

- 문서에는 `<!doctype html>`, 적절한 `lang`, 문자 인코딩, viewport, 의미 있는 `title`을 지정합니다.
- 콘텐츠 구조에 맞는 시맨틱 요소를 사용합니다: `header`, `nav`, `main`, `section`, `article`, `aside`, `footer`.
- 시맨틱 요소가 적절하지 않은 경우 `div`와 `span`을 사용해도 됩니다. `div` 사용 자체를 금지하지 않습니다.
- 제목은 시각적 크기가 아니라 문서 구조에 맞게 `h1`–`h6`를 선택합니다.
- 이동에는 `<a>`, 동작 실행에는 `<button>`을 사용합니다.
- 폼 컨트롤에는 연결된 `label`과 필요한 안내·오류 메시지를 제공합니다.
- 이미지에는 적절한 `alt`를 지정합니다. 장식 목적의 이미지는 `alt=""`를 사용합니다.
- ARIA는 네이티브 HTML만으로 의미나 상태를 전달할 수 없을 때 사용합니다. 불필요한 `role`을 중복 지정하지 않습니다.

## 3. CSS 작성 규칙

### 3.1 네이밍 및 구성

- 기존 프로젝트의 네이밍 규칙을 유지합니다.
- 신규 프로젝트에서는 BEM(`block__element--modifier`)을 선택적으로 적용해 컴포넌트 스타일을 구분합니다.
- 클래스명은 역할과 의미를 설명하도록 작성합니다.
- 공통 색상, 타이포그래피, 간격은 CSS Custom Properties로 관리합니다.
- 높은 우선순위의 선택자, 불필요한 `!important`, 과도하게 중첩된 선택자를 피합니다.

### 3.2 레이아웃 및 반응형

- Flexbox와 Grid를 콘텐츠 구조에 맞게 사용합니다.
- 고정 픽셀 크기를 무조건 사용하지 말고 `%`, `rem`, `minmax()`, `clamp()`, `max-width` 등을 적절히 조합합니다.
- 이미지와 미디어는 컨테이너를 벗어나지 않도록 하고, 원본 비율과 크롭 의도를 확인합니다.
- 브레이크포인트는 프로젝트 명세나 제공된 시안을 우선합니다. 별도 기준이 없다면 콘텐츠가 깨지는 지점을 기준으로 정합니다.
- 데스크톱에서 모바일로 축소할 때 요소 크기만 줄이지 말고 컬럼, 순서, 내비게이션, 간격, 표시 여부를 함께 조정합니다.
- 가로 스크롤이 의도된 UI인지 확인하고, 의도하지 않은 overflow를 제거합니다.

### 3.3 애니메이션 및 렌더링

- 애니메이션은 가능하면 `transform`과 `opacity`를 우선 사용합니다.
- `width`, `height`, `top`, `left`, `margin` 등의 속성 애니메이션을 무조건 금지하지는 않지만, 레이아웃 재계산 비용과 실제 성능을 고려합니다.
- `will-change`는 실제로 필요한 요소에만 제한적으로 사용합니다.
- `prefers-reduced-motion: reduce`를 지원합니다.
- 스크롤·리사이즈 이벤트에서 무거운 DOM 작업을 반복하지 않습니다.

## 4. JavaScript 구현 규칙

### 4.1 기본 원칙

- 기능 단위로 코드를 분리하되, 작은 기능에 불필요한 클래스·모듈을 만들지 않습니다.
- 전역 변수와 전역 네임스페이스 오염을 최소화합니다.
- DOM 선택 결과가 필요 이상으로 반복 사용되는 경우 변수에 저장합니다.
- 요소가 존재하는지 확인한 뒤 이벤트를 연결합니다.
- 이벤트 리스너는 필요한 대상에만 등록하고, 반복 생성·제거되는 UI에서는 정리 방법을 고려합니다.
- `setTimeout`, `setInterval`, `requestAnimationFrame`, `addEventListener` 등은 생명주기가 끝날 때 정리할 수 있도록 관리합니다.
- 사용자 입력을 HTML 문자열에 직접 삽입하지 않습니다. 텍스트는 `textContent`를 우선 사용하고, HTML 삽입이 필요하면 신뢰 가능한 데이터인지 확인합니다.

### 4.2 이벤트 처리

- 리스트처럼 자식 요소가 동적으로 많이 생성되는 UI는 이벤트 위임을 고려합니다.
- 이벤트 위임 시 `event.target`이 텍스트 노드 또는 내부 자식일 수 있으므로 `closest()`와 컨테이너 포함 여부를 확인합니다.
- 모든 이벤트에 이벤트 위임을 강제하지 않습니다. 독립적인 버튼이나 소수의 고정 요소는 직접 바인딩해도 됩니다.
- 이벤트 리스너를 등록한 DOM을 `innerHTML` 등으로 교체하면 리스너가 사라질 수 있습니다. 이벤트 위임을 사용하거나 다시 연결합니다.
- 동일한 이벤트가 중복 등록되지 않도록 초기화 흐름을 확인합니다.

### 4.3 DOM 업데이트

- 정적 마크업은 HTML에 작성하고, JS는 필요한 동작과 동적 콘텐츠를 담당하도록 역할을 나눕니다.
- 반복 렌더링 시 기존 DOM을 무조건 전체 교체하지 말고 변경 범위를 고려합니다.
- `innerHTML`은 고정된 템플릿 또는 안전성이 확인된 콘텐츠에만 사용합니다.
- 필터·탭 등 상태 변화는 단일 상태값을 기준으로 UI를 갱신합니다.
- 브라우저 기본 기능으로 해결할 수 있는 경우 자체 구현을 피합니다.

## 5. 컴포넌트 및 상태 관리

Vanilla 프로젝트에 특정 컴포넌트 프레임워크나 상태 관리 패턴을 강제하지 않습니다.

### 5.1 간단한 UI

필터 하나, 메뉴 토글 하나 등은 일반 함수와 이벤트 리스너로 구현합니다.

```javascript
const menuButton = document.querySelector(".menu-button");
const menu = document.querySelector(".site-menu");

if (menuButton && menu) {
  menuButton.addEventListener("click", () => {
    const isOpen = menuButton.getAttribute("aria-expanded") === "true";

    menuButton.setAttribute("aria-expanded", String(!isOpen));
    menu.hidden = isOpen;
  });
}
```

### 5.2 여러 컴포넌트가 상태를 공유하는 경우

- 공유 상태가 실제로 필요할 때만 간단한 Store 또는 CustomEvent를 도입합니다.
- 상태 변경과 DOM 업데이트의 흐름을 명확하게 유지합니다.
- Store, EventBus, Base Component를 함께 도입하는 것은 복잡성이 이점을 넘어설 때 피합니다.
- 상태 관리 라이브러리를 사용해야 할 정도로 복잡해지면 사용자에게 구조와 도입 이유를 설명합니다.

### 5.3 컴포넌트 클래스가 필요한 경우

- 반복 생성되거나 독립적인 생명주기를 가진 UI에 한해 클래스를 고려합니다.
- 클래스의 초기화, 이벤트 연결, 정리 메서드가 명확해야 합니다.
- `destroy()`에서는 해당 인스턴스가 생성한 이벤트 리스너와 타이머 등을 정리합니다.
- DOM 전체를 지우는 등 부모 컨테이너의 소유권을 침범하지 않습니다.

## 6. 접근성 구현 기준

- 키보드만으로 모든 기능에 접근할 수 있어야 합니다.
- `:focus-visible`을 사용해 명확한 포커스 표시를 제공합니다.
- 메뉴 버튼은 `aria-expanded`와 `aria-controls` 상태를 실제 메뉴 상태와 동기화합니다.
- 탭 UI를 구현할 때만 탭 패턴에 맞는 `role`, `aria-selected`, 키보드 이동을 적용합니다. 단순한 필터 버튼을 탭으로 잘못 표시하지 않습니다.
- 모달은 열릴 때 포커스 이동, 내부 포커스 관리, 닫힐 때 원래 요소로 복귀를 처리합니다.
- 동적으로 바뀌는 결과를 반드시 알릴 필요가 있는 경우에만 `aria-live`를 적절히 사용합니다.
- `aria-hidden="true"`인 요소 안에 포커스 가능한 요소가 남지 않도록 합니다.
- 접근성은 자동 검사뿐 아니라 키보드와 실제 상호작용으로 확인합니다.

## 7. 성능 및 안정성

### 7.1 기본 성능 원칙

- 이미지에는 적절한 크기와 포맷을 사용하고, 화면 아래 이미지에는 필요에 따라 `loading="lazy"`를 적용합니다. 첫 화면의 핵심 이미지는 무조건 lazy-load하지 않습니다.
- 이미지의 `width`와 `height` 또는 `aspect-ratio`를 지정해 레이아웃 이동을 줄입니다.
- 불필요한 라이브러리, 중복 코드, 큰 이미지 파일을 피합니다.
- 스크롤·리사이즈 이벤트에서 레이아웃 측정과 DOM 변경을 반복하지 않도록 합니다.
- `requestAnimationFrame`은 프레임 단위 시각 업데이트가 필요할 때 사용하고, 단순 이벤트에 무조건 적용하지 않습니다.
- 성능 최적화는 추측만으로 하지 말고 실제 병목을 확인한 뒤 수행합니다.

### 7.2 목표 및 검수

Lighthouse 점수는 참고 지표이며 기기, 네트워크, 테스트 환경에 따라 달라집니다. 특정 점수를 기능 구현보다 우선하지 않습니다.

- 성능: 불필요한 리소스와 레이아웃 이동 최소화
- 접근성: 주요 자동 검사 오류 해결 및 수동 키보드 검수
- Best Practices: 콘솔 오류, 잘못된 리소스 경로, 보안·호환성 문제 확인
- 반응형: 주요 브레이크포인트와 중간 너비에서 레이아웃 확인

## 8. 구현 및 검수 워크플로

작업은 다음 순서로 진행합니다.

1. **프로젝트 파악:** 기존 파일 구조, 사용 기술, 클래스명, CSS 규칙, 이미지 경로를 확인합니다.
2. **요구사항 정리:** 수정 대상, 유지해야 할 영역, 화면별 동작, 인터랙션을 구분합니다.
3. **구현 계획:** 변경할 파일과 핵심 로직을 최소 범위로 정합니다.
4. **구현:** 기존 구조를 최대한 유지하며 필요한 부분만 수정합니다.
5. **자체 검수:**
   - HTML 구조와 CSS 선택자 오류
   - JS 문법 및 null 참조 가능성
   - 이벤트 중복 등록과 DOM 교체 후 이벤트 유실
   - 이미지·폰트·스크립트 경로
   - 데스크톱·태블릿·모바일 레이아웃
   - 키보드 조작, 포커스, ARIA 상태
   - 콘솔 오류 및 의도하지 않은 가로 스크롤
6. **결과 보고:** 수정 파일, 주요 변경점, 확인한 항목, 실행하지 못한 테스트와 남은 이슈를 구분해 알립니다.

## 9. AI 작업 우선순위 및 금지 사항

요구사항이 충돌하면 다음 순서로 판단합니다.

1. 사용자가 현재 요청에서 명시한 지시
2. 제공된 기존 코드와 프로젝트 구조
3. 제공된 디자인 시안·기능 명세
4. 이 Spec-Kit의 개발 원칙
5. 일반적인 개발 관행 및 AI의 제안

다음 행동은 사용자의 허락 없이 수행하지 않습니다.

- 프로젝트 전체를 임의로 재작성하거나 파일 구조를 전면 변경
- 프레임워크·패키지·외부 라이브러리의 임의 도입
